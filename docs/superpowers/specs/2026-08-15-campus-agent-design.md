# 校园事务 + 求职成长双引擎助手 · 设计文档

- 日期：2026-08-15
- 状态：已与用户逐节确认，待最终审阅
- 用户背景：大学生，正在学习 Java，希望本项目促进编程学习，未来求职方向为 Java 后端实习/工作

## 1. 项目目标

构建一个跑在本机、面向单用户的私人助手：

1. 接收用户粘贴/上传的课程表、老师通知、作业、考试安排等信息，自动抽取为结构化数据并本地存储；
2. 随时回答「今天上什么课」「还有哪些作业没写」「考试安排」等查询；
3. 定时生成每日早报、作业/考试到期提醒；
4. 定时搜集 Java 实习信息并按用户方向过滤、推送；
5. 围绕 Java 求职目标生成学习计划、记录学习进度；
6. 项目本身作为用户学习 Java 后端（Spring Boot 生态）的载体，最终可写入简历。

## 2. 需求汇总（已澄清）

| 维度 | 结论 |
|---|---|
| 交互渠道 | 本地网页聊天界面；手机同 WiFi 局域网访问 |
| 信息摄入方式 | ① 复制/粘贴文字消息 ② 图片/截图（需 OCR/视觉模型） ③ 文件导入（Excel/PDF/课表文件） ④ 自然语言口述待办 |
| 大模型 | 低价云 API（DeepSeek），少量付费可接受 |
| 运行环境 | 用户电脑每天使用，本地服务常驻可靠 |
| MVP 功能 | 课表问答、作业/待办跟踪、实习信息搜集 |
| 学习计划模块 | 聚焦 Java 编程学习、服务找实习（围绕岗位 JD 制定），不服务学校课程 |
| 技术背景 | 编程水平不高、正在学 Java，可按教程操作，愿意持续维护 |

## 3. 技术选型（对照企业主流，2025）

| 项 | 选择 | 理由 |
|---|---|---|
| JDK | Java 17 LTS（21 亦可） | 新项目主流；Spring Boot 3 要求 17+ |
| 框架 | Spring Boot 3 | 企业 Java 后端事实标准 |
| 构建 | Maven | 国内企业占比约七成，招聘最常见 |
| 持久层 | MyBatis-Plus | 国内招聘 JD 最高频 ORM；官方支持 SQLite 方言。阶段 1 先用裸 JDBC 打 SQL 基础（MyBatis-Plus 教程均基于 Spring Boot），阶段 2 引入 Spring Boot 时启用 |
| 数据库 | SQLite（阶段 6 可迁移 MySQL） | 本地零运维单文件；MyBatis-Plus 使迁移成本极低，迁移本身是简历亮点 |
| 模型 | DeepSeek API（JSON 输出模式） | 便宜、够强；无视觉能力，图片识别另行选型带视觉的模型 API |
| 前端 | 单页 HTML + 原生 JS | 刻意做薄，学习重心在 Java 后端 |
| 其他 | Git 版本管理（阶段 0 建立） | 企业必备技能，项目即练习 |

### 刻意不做（YAGNI）

- 用户登录系统、多用户
- 云同步、多设备数据同步
- Docker 部署（列为阶段 6 可选演进）
- 微信接入（个人号无官方 API，有封号风险）
- 微服务、Redis、MQ 等中间件（个人项目用不上）

## 4. 总体架构

```
浏览器（电脑 / 手机同WiFi）
└─ 聊天页（HTML+JS 单页）──REST + SSE（流式回复）──▶ Java 应用（Spring Boot）
      ├─ 聊天接口层：收消息、流式回消息
      ├─ 信息摄入引擎：意图分类 → LLM 抽取 → Schema 校验 → 入库
      ├─ 问答引擎：检索 + LLM 综合
      ├─ 定时任务：早报 / 到期提醒 / 实习搜集
      └─ 模型客户端：DeepSeek API 封装
            │
            ▼
SQLite（agent.db 单文件，本机）
```

设计原则：**前端极薄、后端 Java 全包、数据一个 SQLite 文件**，90% 学习时间落在 Java 后端。

## 5. 数据模型（核心表）

| 表 | 内容 |
|---|---|
| courses | 课程（名称/老师/教室/周几 weekday/开始结束时间/周次 weeks） |
| course_overrides | 课程单日临时变动（override_date/kind=cancel或move/新时间地点），按日期作用，过后自动恢复默认课表 |
| semester | 学期配置（单行：start_date 开始日期/total_weeks 总周数），由聊天"设置学期"写入 |
| reports | 每日早报（report_date 唯一 + content），定时生成/懒生成兜底 |
| assignments | 作业（课程/内容/布置日期/截止时间/状态） |
| exams | 考试（课程/日期/地点/形式） |
| todos | 通用待办（内容/截止/优先级/状态/来源） |
| messages | 聊天记录（原文/解析结果/时间） |
| events | 其他日程（活动/老师通知原文存档） |
| internships | 实习信息（company/position/city/salary/deadline/jd 原文/link/status：new 默认，标记后置） |
| profile | 求职档案（单行：skills/target_role/target_city/grade），聊天"设置档案"写入 |
| study_progress | 学习打卡（study_date/context，date 缺省记今天） |
| study_plan | 学习计划任务表（**后置**：v1 学习计划以文本生成存 messages，不建表） |
| raw_inbox | 未解析成功的原始消息（兜底存档） |

设计原则：

1. 每条记录带来源消息 ID，可回溯原文查证；
2. 原文永远存档，解析失败也进 raw_inbox，绝不丢数据；
3. 日期统一解析为具体日期（含时区），「今天/明天/下周」由 LLM 抽取时落地；
4. 状态字段完备：作业/待办 pending/done，实习信息 已投/已收藏/忽略。

## 7. 核心流程

### 7.1 信息摄入（项目心脏）

```
你的消息 → ①意图分类（记录? 提问?）
         → ②LLM 按 Schema 抽取结构化 JSON
         → ③Java 侧校验（必填字段/日期格式）→ 失败重试 1 次
         → ④入库
         → ⑤返回确认回执：「✅ 已记录：高数作业《习题5.2》，截止 11-20 23:59」
         → ⑥用户可回复纠正：「不对，是11-21」→ 更新记录
```

关键设计：**回执 + 可纠正**——每条记录当场回执，错了立刻可改，这是用户信任的来源。解析仍失败的原文进 raw_inbox 兜底。

### 7.2 问答

```
提问 → LLM 判断需要哪些数据 → SQLite 检索相关行
     → LLM 综合数据生成回答（标注来源）→ 答案 + 数据卡片
```

「今天有什么课」类问题：服务端先按**当天星期几**查默认课程，**按学期周次过滤**（courses.weeks 匹配当前周才保留，支持 "1-16"/"1-8,10-16"/单双周语法；未设置学期不过滤，未开学或假期无默认课程），再**应用当日 course_overrides 变动**（取消→剔除；改时间/地点→替换），把"当日有效课程"作为上下文交给 LLM。变动按日期作用，日期一过自动失效、恢复默认——无需任何清理逻辑。

**记录管理（纠正/删除）**：用户可在对话中按「类型+编号」操作记录（如"把作业第3条的日期改成11月12日"、"删除待办第5条"）。分类器识别 correction/delete 意图 → LLM 结合记录列表输出 type+id → 服务端无状态地执行更新或删除。删除回执必须带被删内容（标题/类型）以便误删补救。

### 7.3 定时任务与早报

- **每日早报（已实现于阶段 3）**：每天 07:00 定时生成，存 reports 表（report_date 唯一）；内容包括今日课程（含变动）、今日/3 天内到期作业、7 天内考试、今日待办；打开网页即见，电脑未开机时访问页面懒生成兜底（幂等）。
- **到期提醒**：体现在早报中（作业默认提前 3 天、考试提前 7 天进入早报，窗口后续做成可配置）。
- **实习信息（阶段 4，粘贴 JD 为主）**：用户粘贴岗位 JD → 结构化入库 internships（company/position/city/salary/deadline/jd 原文/link/status）。定时联网搜集后置（需另注册搜索 API，届时评估）。

### 7.4 求职成长（阶段 4）

- **求职档案**：单行 profile（技能/目标岗位/城市/年级），聊天"设置档案"写入。
- **三个按需能力（均流式）**：
  - 匹配度分析：最新实习 JD + 档案 → LLM 输出评分、已满足项、差距清单与补课建议、近 2 周三件事；
  - 学习计划：JD + 档案 → LLM 生成 4 周可执行任务（按周拆分）；计划以文本存 messages，不建任务表（YAGNI，打卡数据积累出真实需求后再建）；
  - 周复盘：近 7 天打卡记录 → LLM 总结亮点/不足与下周建议。
- **每日打卡**：study_progress（date 缺省记今天、context——只记学了什么，不含时间词）；状态标记（已投/收藏）与 JD 去重后置小修。
- **设计原则**：会反复查询/需要状态流转的存表；一次性生成品只存聊天记录。

## 8. 错误处理策略

| 场景 | 处理方式 |
|---|---|
| LLM 返回格式不合规 | Schema 校验失败 → 重试 1 次 → 仍失败进 raw_inbox，回复「未解析，已存档」 |
| API 超时/欠费 | 明确报错「模型服务不可用」，消息本身已存 messages 表不丢 |
| 数据库异常 | 写操作走事务；SQLite 开 WAL 模式防锁 |
| 用户纠正记录 | 更新对应记录并回执新值 |
| 数据混乱 | 每条记录带来源消息 ID，随时回溯原文 |

核心原则：**数据永不丢、模型错了可纠正、系统错了看得见**。

## 9. 测试策略（从阶段 1 开始）

- JUnit 单元测试：抽取结果 Schema 校验、日期解析、存储往返（写入→读出正确）；
- 样例数据测试集：10 条典型老师消息（如「下周一下午两点在A201开会」「11月20日前交实验报告」），改代码后回归；
- 人工验收：每阶段结束亲手走核心场景（录入课表→问今天上什么课）；
- 刻意不做：自动化 UI 测试、覆盖率指标（YAGNI）。

## 10. 隐私与备份

- 数据全在本机 agent.db，备份 = 复制该文件（可选加定时自动备份任务）；
- 局域网访问加简单口令；
- 老师信息等个人数据不上任何第三方平台（仅模型 API 传输必要文本）。
