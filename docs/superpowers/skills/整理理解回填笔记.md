# Skill：整理理解回填笔记

> 用途：每次执行层导师带用户完成一段“理解回填”后，把当天知识点和答错点整理成 markdown 笔记。
> 适用：ExtractedItem、Database、StoredItem/ItemRepository 等已写代码的逐行讲解，以及后续 Task 的理解回填。

## 触发时机

- 用户完成一个文件/一个 Task 的理解回填后，说“整理笔记”“追加笔记”“休息前总结”等。
- 用户明确要求“参考之前的笔记风格”。

## 笔记存放位置

- 用户学习笔记：`docs/notes/`
- 命名建议：`YYYY-MM-DD-phaseN-taskN-主题.md`（阶段 4 起执行层与 v4-pro 确认的命名；阶段 1 用 `-backfill` 后缀的历史文件保留原样）
  - **必须带阶段前缀**：阶段 1 用 `phase1-`，阶段 2 用 `phase2-`，以此类推。
- 参考已有文件：`docs/notes/2026-08-20-day5-phase1-task6-backfill.md`、`docs/notes/2026-09-02-phase4-task7-internship-panel.md`

## 笔记结构（固定模板）

```markdown
# 第 N 天总结：理解回填 · 主题（日期）

> 今日状态：...（测试状态、进度、是否提交）

## 今日范围

- 文件路径列表

## 今日知识点

- 按概念/方法/文件顺序编号
- 每个知识点写“是什么 + 为什么这么写 + 关键细节”
- 涉及代码时给最小示例，不贴整份文件

## 文件与方法链路

- 列出本 Task 涉及的文件，以及每个文件负责什么
- 画出文件之间的调用/依赖关系
- 对每个主要方法，写清：输入 → 做什么 → 输出/调用谁
- 目的是让用户对整个 Task 的“框架”有清晰认识，而不是只看到零散知识点

## 今天答错的点（复习重点）

- 列出用户第一次回答不准确/被纠正的内容
- 每条写：错误说法 → 正确说法 → 为什么错

## 明日接续点

- 下一步计划
- 遗留问题/测试覆盖缺口
```

## 整理要点

1. **知识点按“由易到难、按文件顺序”组织**。
2. **必须包含用户第一次答错或追问过的点**，这是复习价值最高的部分。
3. 对每个答错点，写清“用户原话/错误理解”和“正确理解”，不要只写正确结论。
4. **每个 Task 都要有“文件与方法链路”**：文件职责、文件间关系、主要方法职责和调用链；**链路图要详细**，写出每一步输入、处理、输出，避免只画几个框。
5. 如果当天有排障，单独列一节“排障记录”，包含：报错、根因、修复、教训。
6. 如果用户要求“追加”，在已有笔记中插入新章节，并同步更新标题、状态、范围。
7. 不替用户写代码；笔记可以给代码片段，但目的是解释，不是让用户照抄。
8. 完成后告知用户文件路径，并可提醒是否提交（docs: 前缀）。
9. **笔记文件名必须带阶段前缀**：`phase1-` / `phase2-`，例如 `2026-08-22-phase2-task5-chat-page.md`。

## 协作模式（阶段 4 起固化，用户 2026-09-02 确认）

- **导师建框架、学员填正文**：导师按固定模板建好笔记框架（每节带 `<!-- 正文待填：提示 -->` 引导），学员用自己的话填正文，填完删提示行，导师逐节验收。
- 导师给提示（这节该覆盖什么），**不给正文**——正文必须学员自己写（同"不替用户写代码"原则）。
- 学员可以要求调整结构（增删节、合并知识点），导师按学员判断改框架。
- **「今天答错的点」是固定节，不能省**：概念理解类答错（如 jsonPath 术语、filter 防 null）放这里；代码报错类（编译错、测试红）放"排障记录"——两类分开。
- 验收标准：学员能用自己的话讲清每节，且填的内容与当天实际一致（不抄提示、不编造）。

## 反馈原则（用户 2026-08-20 提出）

- 如果用户的回答**没有任何问题**，那么导师的反馈应当**完全按照用户的说法来**，或者只做**很小的措辞修改**，不要重写成另一套标准答案。
- 目的是让用户保留自己的理解方式，而不是被导师的“标准说法”替代。
- 只有在用户确实理解有偏差时，才指出错误并给出修正。
- **术语性小修（如"JSON 字符"vs"JSON 值"）也算重写**：除非术语错误会导致后续理解偏差，否则按用户说法确认，不抠字眼。

## 提问纪律（用户 2026-08-22 强调）

- **问完问题后必须停住，不能在同一条消息里写答案，也不能写“过关”。**
- 必须等用户回答后，再判断是否理解正确。
- 如果用户答对，按用户的说法确认；如果答错，只指出错误和提示，不直接替用户说完整答案。

## 带任务工作流程（用户 2026-08-28 强调）

1. **先讲概念**：每个 Task 先讲清楚核心概念，用费曼法让学员复述。
2. **列出需要的文件路径和文件名**：在问“创建还是自己写”之前，先把本 Task 要涉及的文件清单列出来。
3. **问学员：创建还是自己写**：不要默认代写，也不要默认让学员写，先问。
4. **逐个文件讲**：创建/写完后，按文件一个一个讲，不要一次倒一大堆。
5. 每个文件讲完确认理解后再进入下一个文件。
6. **先讲完再提交**：所有文件讲完并确认理解后，才整理笔记/提交，不能跳过讲解直接提交。



## 示例片段

```markdown
## 今天答错的点（复习重点）

1. **record 有 setter？** 错。record 没有 setter，创建后不可变；取值方法叫 `type()` 不叫 `getType()`。
2. **`keys.getLong(1)` 的 `1` 是列名？** 错。是第 1 列。
```

## 提交建议

- 笔记属于文档变更，commit message 用 `docs:` 前缀。
- 提交前先 `git status --short` 检查。
- 如果用户想自己练习 git，可把提交动作留给用户。
