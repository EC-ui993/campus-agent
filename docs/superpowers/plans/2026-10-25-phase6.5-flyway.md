# 阶段 6.5：Flyway 迁移引入（schema 版本化）· 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 schema 演进从"人肉对齐多处 CREATE IF NOT EXISTS"升级为 Flyway 版本化迁移——现在已有 3 处 schema 来源（本地 agent 库、Compose 的 mysql-data、测试 TempDb），且已真实咬过一次（agent_test 旧表 TEXT 报 1170）。本阶段后：**一份 V1__init.sql 是唯一 DDL 来源**，本地与 Compose 由 Flyway 管，测试 TempDb 继续翻译同一份文件（保持 P2 单份性质）。

**Architecture:** flyway-core + flyway-mysql（Boot 3.5 管理版本；Flyway 10+ 的 MySQL 支持在独立模块 flyway-mysql，**必须两个依赖都加**）；`src/main/resources/db/migration/V1__init.sql`（= 现有 schema.sql 内容整体平移）；既有库用 baseline（无 flyway_schema_history 的老库不重放 V1）；测试侧不引入 Flyway，TempDb 翻译器改读 V1 文件。

**Tech Stack:** Flyway（Boot 托管版本）、既有 Spring Boot 3.5 + MySQL 8.4。

## 执行纪律

- 概念先行 + 费曼复述；TDD 不适用（基建迁移），验收靠三环境实测 + 一次 V2 演练。

## Task A: 概念启蒙（无代码）

- [ ] **概念清单（学员复述过关）**
  - **CREATE IF NOT EXISTS 的盲区**：只保证"表在"，不保证"结构对"——旧表缺新列时静默跳过，正是 agent_test 咬人的 1170 的来源；迁移工具 = schema 的版本控制系统（像 git 管代码一样管建表历史）
  - **Flyway 核心术语**：migration 脚本（V1__、V2__…）、flyway_schema_history 表（已应用版本清单 + checksum）、baseline（把已有老库标记为某版本，不再重放之前的脚本）、checksum 校验（改过已应用的脚本会报错，防漂移）
  - **为什么现在上**：3 处 schema 来源已是事实；且 4.8（course_override 加字段）是第一次真实 schema 变更，正好用 V2 做第一次真实迁移
  - **Flyway 与 Spring 的关系**：Boot 启动时自动发现 classpath:db/migration 并执行；`spring.flyway.*` 配置项

## Task B: 引入 Flyway（本地 + Compose）

- [ ] pom 加依赖：`org.flywaydb:flyway-core` + `org.flywaydb:flyway-mysql`（版本由 Boot BOM 管，不写版本号）
- [ ] 建 `src/main/resources/db/migration/V1__init.sql`：现有 schema.sql 内容整体平移（MySQL 方言；删除旧 schema.sql 或留一行指针指向 V1——推荐直接删除，杜绝双文件）
- [ ] application.yml：删 `spring.sql.init`（建表权交给 Flyway）；加 `spring.flyway.baseline-on-migrate: true`（老库无 history 时自动 baseline 不报错）
- [ ] 三处库的处置（学员操作，flash 引导）：
  - 本地 `agent` 库：已有表、无 flyway_schema_history → baseline-on-migrate 自动处理；启动验证聊天/早报正常
  - Compose `mysql-data`：同 baseline（或直接 `docker compose down -v` 重建——**注意 -v 会删数据卷**，本地已搬运的数据若在卷里需先确认；推荐 baseline 保数据）
  - 确认 `flyway_schema_history` 表在启动后出现且记录 V1 一条
- [ ] 验收：两环境启动成功，`SHOW TABLES` 见 flyway_schema_history；业务功能回归正常

## Task C: 测试侧对齐（保持 P2 单份性质）

- [ ] TempDb 翻译器改读 `db/migration/V1__init.sql`（不再读旧 schema.sql）；翻译规则不变
- [ ] `mvn test` 全量绿（9 个碰库测试类 + 其余全部）
- [ ] 说明（学员复述）：为什么测试不直接用 Flyway——SQLite 方言翻译器 + ScriptUtils 已够快够简单；Flyway 管的是"真实环境的历史演进"，测试只需要"当前结构的临时库"
