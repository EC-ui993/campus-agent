## Bug 1：本周课表起点不对

**现象**：开学（9月7日）前点"本周课表"，应从开学第一周（9月7日）开始显示，实际从当前日期所在周（8月24日）开始。

**排查过程**（分层排障，从里到外）：
1. 数据层：SQL 查 `semester` 表 → `start_date = 2026-09-07, total_weeks = 16` ✅ 数据对
2. 逻辑层：读 `ChatController.weekSchedule()` 代码，确认 `if (今天早于学期开始) → 用开学日那一周的周一作起点` 逻辑在
3. 重启验证：跑旧代码，9/7 出现

**根因**：代码逻辑没问题，是**没重启**导致跑的是旧代码。

**验证**：重启后第一条日期 = 2026-09-07、状态"第1周" ✅

**修复**：`weekSchedule()` 加 `semester` 判断 + `previousOrSame(MONDAY)` 兜底。

**教训**：改完代码必须完整重启再验证；排查先看数据层（一条 SQL 排除一大片）。

## Bug 2：问"9月8日有什么课"只列 1 节

**现象**：数据库周二有 4 节课（weekday=2、weeks=1-16），LLM 回答只列了 1 节且序号是 4。

**排查过程**：
1. 数据层：SQL 确认 courses 表周二 4 条 ✅
2. 组装层：在 `llm.chatStream` 前打印拼好的 prompt → LLM 输入里 **4 个课程 JSON** ✅
3. 提示词层：读 `Prompts.ANSWER` 原文 → 只有"回答简洁"指令，没有"全部列出"

**根因**：`Prompts.ANSWER` 里"回答简洁"与"列出全部"冲突——模型服从"简洁"就省略，只摘了最后一条（所以序号是 4）。

**修复**：加条件指令"如果用户询问某天的课程安排，把当天课程全部列出来，不要省略，其它情况回答简洁"。

**教训**：症状在最外层，根因可能在任何一层——分层验证（SQL/打印输入/读提示词），不许跳层；改提示词前先确认上下文里到底有几条。

## Bug 3：提示词修好后"列出来又没了"，只剩最后一节（Bug 2 第二层）

**现象**：重新问"9月8日有什么课"，模型开始列全部课程了，但流式显示时"前面几节课刚列出来就没了"，最后只剩最后一节。

**排查过程**：
1. 服务器侧证据：DB 里存的回复是完整 4 节 → 服务器没问题
2. 前端渲染层：读 `index.html` SSE 处理代码 → 发现 done 事件处理逻辑
3. DevTools Network 看线上格式：done 事件的数据因含换行被拆成**多条 `data:` 行**

**根因**（两层）：
- 服务器把完整回复装进 `event:done` 事件，回复含换行 → 被拆成多条 `data:` 行
- 前端收到 `event:done` 置 `finished=true` → 之后每条 `data:` 执行 `textContent = 新值`（整体替换）→ 逐行覆盖，只剩最后一行
- 顺带发现：流式阶段换行符被丢弃（每条 data 直接 += 没补 \n）

**修复**（方案 3，统一全流式）：
- 后端：删掉 `event:done` 发送（它是冗余的——done 数据 = 流式内容复读）
- 前端：按"空行 = 一条 SSE 事件结束"攒行、`join("\n")` 还原换行，一次追加；流结束靠 `reader.read()` 的 done（不是 event:done）

**验证**：4 节全列、每节一行、中间空行正确、无重复 ✅

**教训**：
- SSE 协议：空行 = 事件边界；`reader.read()` done = 流结束；一个事件可以有多条 data 行
- 删掉一个发送通道前，想清楚它是不是某些路径的唯一通道

## Bug 4：纠正/删除序号错位（"改 #4 却改了 #1"）

**现象**：发"把序号为4的任务内容改为习题6.6"，结果 #1 被改了；试其它序号也错位。

**排查过程**：
1. 先排除"序号越界"（删过记录）：记录面板有 21 条，足够 4 条 → 排除
2. 控制台打印 `correct()` 各分支 → 走到"✅ 已更新"但改错对象
3. 读 `ItemRepository.allItems()` 源码 → 发现按类型分组遍历、每类 `selectList(null)` 无 ORDER BY

**根因**：
- `allItems()` 按类型分组（assignment → exam → todo → course → event）、无 ORDER BY，返回顺序不保证稳定
- `recordsWithSeq()`（给 LLM 编号）和 `resolveIdBySeq()`（序号 → 真实 id）**各调一次 allItems()**，两次调用间数据一变顺序就不同 → 序号对不上 id

**修复**（方案 B：数据快照一致性）：
- `recordsWithSeq()` 结果存成 `snapshot`，在 LLM 调用前定格
- `resolveIdBySeq(snapshot, type, seq)` 改为接收快照参数，不再自己查库 → 变成**纯函数**（只靠参数、不碰 repo）
- `correct()`/`delete()` 里 LLM 看到的列表和解析用的是**同一份快照**

**验证**：修正后"改 #4"正确改到第 4 条；删一条再试，序号前移后仍正确 ✅

**教训**：
- 序号不该由"遍历位置"决定——要有稳定映射
- 两次调用之间数据可能变化，快照必须在 LLM 前定格
- 排障时"没找到"和"改错对象"是不同症状，先取证再判断

## Bug 5：`m.get(type)` 笔误（修 Bug 4 时引入）

**现象**：方案 B 改完后，`correctionFlowUpdatesById` 和 `deleteFlowRemovesRecord` 两个测试红："没找到编号为 1 的 assignment 记录"。

**排查过程**：
1. 读 `resolveIdBySeq` 新实现 → 第 265 行 `if (type.equals(m.get(type)))`
2. 对照 `StoredItem.toMap()` 键名（"id"/"type"/"title"…）

**根因**：`m.get(type)` 中 `type` 是变量（值 `"assignment"`），实际在找键 `"assignment"`——map 里**没有这个键** → 返回 null → `"assignment".equals(null)` 恒 false → index 永远是 0 → 永远返回空。

**修复**：`m.get(type)` → `m.get("type")`（一个引号之差）。

**验证**：两个测试变绿，全量 60 绿 ✅

**教训**：Map 取值先确认键名；`equals(null)` 恒 false 是 Java 陷阱；条件恒 false 会让方法永远走失败分支——这种 bug 症状像"记录不存在"，其实和记录无关。

## Bug 6：录入/纠正/删除"无回复"（方案 3 的代价）

**现象**：修 Bug 3（删 done 发送）后，record/correct/delete 三条路全部"无回复"，且纠正"没执行"。

**排查过程**：
1. 控制台证据：`correction` 意图打印出现，但 `correct()` 分支打印没有 → correct() 没执行？→ 其实执行了（`✅ 已更新` 打印）
2. 读 `handleStreaming` → else 分支 `return switch(...)` 只是返回字符串，**从不调用 onDelta**
3. 回忆方案 3 前：非流式分支靠"返回值 → 装进 done 事件"送达；删了 done，通道就没了

**根因**：方案 3 删掉 done 发送时，**默认了非流式分支也在流式**——但它们从不调 `onDelta`。删 done = 拆掉三条路的唯一传输通道 → 服务器什么都没发 → "无回复"。

**修复**：三个分支算完 reply 后 `onDelta.accept(reply)`（补上通道）；switch 表达式块形式用 `yield` 返回值（return 是方法级的，yield 是 switch 级的）。

**验证**：三条路都有回复 ✅

**教训**：删代码前想清楚"它是不是某些路径的唯一通道"；"无回复"要先区分"没执行"和"执行了但没显示"（看数据库/面板 vs 看网络/控制台）。

## Bug 7：拖拽高度写反（UI 改进时）

**现象**：早报拖拽手柄，向下拉显示部分反而减少。

**根因**：屏幕坐标 `clientY` **向下增大**——下拉时 `clientY - startY` 是正数，代码写 `startH - 位移` → 高度变小。方向反了。

**修复**：`startH + (clientY - startY)`——下拉（正位移）→ 高度增大；上滑（负位移）→ 高度减小，同一公式靠正负号处理两个方向。

**验证**：下拉展开、上推收起 ✅

**教训**：写拖拽/滚动类交互，先想清楚坐标正方向再定加减号。

## Bug 8（阶段 3.6）：纠正时 title/content 字段语义歧义

**现象**："把第24条作业内容改成2.2"→ 改了 content（详情），用户以为改 title（标题），且回执看不出改了什么。

**根因**（产品设计缺陷，不是代码 bug）：
- 提示词没钉死 title/content 语义 → LLM 对"内容"指代判断随意
- 回执只显示"改后长什么样"，不显示"什么从什么变成了什么" → 误判不可见
- 空纠正（"改一下"但没具体说改什么）谎报"✅ 已更新"

**修复**（两层防御）：
1. **提示词收窄歧义**：EXTRACT 钉死 title = ≤15 字短标题 / content = 完整内容；CORRECT 加指代规则（标题/名字→title，内容/要求/详情→content，日期→dueDate，地点→location）+ 默认规则（短描述归 title）
2. **回执透明化**：diff 回执"字段名：旧值 → 新值"，只列有变化的字段；空纠正诚实回复"没有需要修改的内容"（附当前记录）

**验证**：真实 LLM 四场景走查通过（未指代归 title / 指日期只改日期 / 指内容只改内容 / 空纠正诚实）✅

**教训**：LLM 歧义无法 100% 根除（中文灵活），两层防御：提示词收窄 + 回执兜底；"改没改"要用证据判断（控制台/面板/回执），不能凭感觉。

## 排障方法论沉淀（贯穿所有 bug）

1. **分层排障**：数据层 → 逻辑/组装层 → 提示词层 → 显示层，从里到外，每层有独立验证手段（SQL / 打印输入 / 读提示词原文 / 看 Network 响应体），不许跳层
2. **先取证再判断**：测试红不一定是产品代码错（可能是测试数据没搭对）；"没执行"和"执行了没显示"要分开取证
3. **改动前想清影响面**：删一个通道前确认它是不是某些路径的唯一通道（方案 3 的教训）
4. **测试是回归防护**：TDD 红→绿流程能抓住"规则被删""条件恒 false"这类隐蔽回归
5. **可观测性**：错误分支要有可区分的文案/打印（"id 映射失败" vs "记录查询失败"），运行时才知道走到哪
