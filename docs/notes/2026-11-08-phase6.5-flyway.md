## 一、为什么需要它：`CREATE TABLE IF NOT EXISTS` 的盲区

它保证的是 **"表存在"**，不是 **"结构对"**。

```
你改了 schema.sql（加列 / 改类型）
旧表没有这个改动
→ IF NOT EXISTS 看到表在 → 跳过
→ 【成功。零输出。什么提示都没有】
→ 你确信"改好了"
→ 几周后某条真正需要那个改动的语句才炸
```

**两个要素合起来才是"静默漂移"**：

1. **判断依据只有「表名存在」** ✗ —— 不看列、不看类型、不看索引
2. **不报错** ✗ —— 跳过的决定没有任何输出

**后果**：错误的发生点（改 schema）和发现点（几周后一条 SQL 报错）离得很远，而且报错信息指向别处（`agent_test` 那次报的是 **1170**"TEXT 列不能建索引"，根本不提"表结构过期"）。

> **幂等 ≠ 版本管理。前者防重复，后者才防漂移。**

## 二、四个术语

| 术语 | 是什么 | 类比 |
|---|---|---|
| **migration 脚本** | `V1__init.sql`、`V2__add_demo_column.sql` | 一次 commit |
| **`flyway_schema_history`** | 已应用版本清单 + checksum + 成功标记 | `git log` |
| **baseline** | 把已有老库标记为"已在某版本"，之前的不重放 | 给老仓库补初始 commit |
| **checksum** | 每个脚本内容的指纹 | commit hash |

启动动作：读 `db/migration` 下所有 `V*.sql` → 对比账本 → **只跑没跑过的，按版本顺序** → 记账。

## 三、baseline 为什么必须设成 0

老库（有表、无账本）直接跑 V1 会撞上已存在的表。`baseline-on-migrate: true` 让它"先把现状登记成某版本"，然后往后应用。

**关键在版本号**：

| `baseline-version` | 结果 |
|---|---|
| `1`（默认） | V1 被跳过 → 账本里只有一条 `<baseline>`，**永远没有 V1 记录** |
| **`0`** | 先登记 baseline=0 → **V1 真实执行**（`IF NOT EXISTS` 全跳过，无害）→ 账本里有真正的 V1 |

实测账本（两库一致）：

```
1 | 0 | << Flyway Baseline >> | BASELINE | 1
2 | 1 | init                  | SQL      | 1
3 | 2 | add demo column       | SQL      | 1
4 | 3 | drop demo column      | SQL      | 1
```

> `description` 来自文件名：`V2__add_demo_column.sql` → `add demo column`（下划线转空格）。所以文件名要用**有意义的英文短语**，账本读起来就是 changelog。

## 四、本阶段最有价值的发现：两道检查的强度不对称

Task D 做了两次实测（都是真实跑出来的，不是推断）：

| 你做的事 | Flyway 反应 | 数据库会坏吗 |
|---|---|---|
| **删掉已应用的 V2 文件** | ⚠️ **不管**。只报 `Current version of schema: 2`，然后 `Schema is up to date. No migration necessary.`，**正常启动** | **不会**——结构没变，丢的只是溯源信息 |
| **改掉已应用的 V2 内容** | ❌ **拒绝启动**：`Migration checksum mismatch for migration version 2` / `Applied to database: 2060458392` / `Resolved locally: -1615501833` | **会**——同一版本号在不同环境跑不同 SQL |

**为什么这样设计？** 判断标准不是"文件在不在"，而是**"同一个版本号会不会导致不同环境结构分叉"**：

- 缺文件 → 结构一致 ✓ → 可容忍 → 警告级别
- 改内容 → 结构分叉 ✗ → 灾难 → 必须拒绝

**所以纪律要分清哪条由工具守**：

1. 不要改已应用的脚本 → **机器拦** ✓
2. 不要删已应用的脚本 → **只能靠人守** ⚠️
3. 回滚 → 写新版本（下面说）

## 五、回滚的真相：只向前

**Flyway 没有"回滚"这个功能** ✗ —— 所谓回滚 = **写一个新版本，做相反的操作**。

演练：`V2` 加列 → `V3` 删列 → 结构回到 **V1 等价**，但账本保留 **4 行**。

> **"V1 等价" ≠ "V1 状态"。** 结构一样，账本更厚。
> 这是**特性**：任何机器从 V1 往上跑，都会经过"加列→删列"这条真实路径，最终结构与你的完全一致。

**误改之后的正确修法**：把内容**改回原样**，checksum 自然重新匹配——不需要 `flyway repair`（它只改账本里的校验和，**不改数据库**，等于睁一只眼）。

## 六、测试为什么不用 Flyway

| | 要什么 |
|---|---|
| **测试 `TempDb`** | 一个"**当前结构**的空库" |
| **Flyway** | "**历史演进**"的正确性 |

测试每次从零建库，没有历史，也就无所谓版本。

**一致性靠的是：`TempDb` 按序重放「全部」迁移脚本** —— 单份 DDL 是底座，Flyway 和翻译器都从它出发。

### 这里差点留下一个洞

计划 Task C 的原话是「TempDb 翻译器**改读 V1**」。照字面做，洞是这样的：

- 测试库 = **只有 V1 的结构**
- V2 之后任何**净增加**的变更（比如加一列）都到不了测试库 ✗
- 当时没暴露，只因为 V2/V3 的**净效果为零**（加列又删列）
- **4.8 给 `course_override` 加字段那天就会现原形** ✗ —— 测试跑在"少了列"的库上，可能一路绿到线上出问题

**修法**：`TempDb` 遍历 `db/migration/V*.sql`，**按版本号数值**排序，逐个翻译 + 执行。

> ⚠️ **必须按数字排序，不能按文件名**：字典序里 `V10` 排在 `V2` 前面 ✗ —— 迁移顺序会全错。

这样"当前结构"才真的是"所有迁移叠加后的结构"，单份来源的性质才真正保住。
实测：V2 加列、V3 删列在 SQLite 上也能正确重放，`mvn test` 83 绿。

## 七、踩坑记录

### 坑 1：翻译器没跟上新语法 → 56 个测试红

加索引时往 `schema.sql` 写了 MySQL 的**行内索引**：

```sql
CREATE TABLE assignments (
  ...
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_assignments_due (due_date, due_time)   ← SQLite 不认
)
```

SQLite 报 `near "due_date": syntax error`。

**修法**：翻译器加第 4 条规则，把 `, KEY name (cols)` 整条删掉。

> **为什么可以直接删**：索引只影响**性能**、不影响**行为**；测试库不需要。而 `UNIQUE` 是**列约束**不是 `KEY` 子句，会原样保留。

**这条暴露了"一份 DDL + 翻译器"的真实维护成本**：每次 schema 用新语法，翻译器就得跟。它比"两份 DDL"好（不会静默分叉），但**不是零成本**。好在失败是**响亮的**（SQLite 当场报错）。

### 坑 2：`src/` 不是运行时读的地方

把 `V2` 从 `src/main/resources/db/migration/` 挪走后重启，**Flyway 照样认 V2** ✗。

原因：运行时读的是 **`target/classes/db/migration/`**（构建产物）。`resources:resources` 只做**复制**，**不做同步删除**——src 里删掉的文件，target 里那份还在。

**必须 `mvn clean`** 才会消失。

> **"我明明删了，怎么还在生效？"——答案永远是：产物还在。**
> 同一家族：改了 `index.html` 刷新无效、Docker 里跑了旧 jar。

### 坑 3：镜像 = 某一刻的快照

V3 加完之后 `docker compose up -d --build`，Compose 账本**还是停在 V2** ✗ —— 因为**上一次 build 是在 V3 存在之前**做的。

**每加一个 migration 都要重建镜像**（SQL 打在 jar 里），改完必须 `--build`。

### 坑 4：`mvn spring-boot:run` 直跑没有 `DB_PASSWORD`

```
Access denied for user 'campus'@'172.17.0.1' (using password: NO)
```

`DB_PASSWORD` 是 `start.ps1` 设的，绕过它就没了。

**顺带一个实测证据**：MySQL 眼里来源是 **`172.17.0.1`（Docker 网桥网关）**，不是 `127.0.0.1` —— 这正是阶段 6 里为什么必须用 `'campus'@'%'` 而不是 `@'localhost'` 的原因（当时只是推理，现在有实测）。

### 坑 5：版本组合未经验证

```
Flyway upgrade recommended: MySQL 8.4 is newer than this version of Flyway
and support has not been tested. The latest supported version of MySQL is 8.1.
```

Flyway 11.7.2 + MySQL 8.4。功能正常，但**真出诡异问题时这是第一怀疑对象**。

### 坑 6（关于导师的）：两次预判都被实测推翻

| 我的预判 | 实测 |
|---|---|
| 删掉已应用的迁移会**拒绝启动** | ✗ 正常启动，只报 `Current version` |
| "改了已应用脚本"和"删了"都会拦 | ✗ 只有改内容才拦 |

**两次都是先有推断、后被证据推翻。** 而证据只花了三条命令（看 `src`、看 `target`、读 `run.out`）。

> **推断可以指导你去哪找证据，但推断本身不是结论。**
> 笔记里凡是"实测结论"，都要能指出是哪条命令、哪段日志得出的。
