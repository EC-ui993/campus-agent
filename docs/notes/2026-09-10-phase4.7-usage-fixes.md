## 今日知识点

### 1. 意图分类的覆盖完整性（record 漏了实习）

- 现象：粘贴一条完整 JD（含"实习生/岗位职责/任职要求"）→ 被判成求职能力意图 → 回"还没有实习记录"
- 根因：CLASSIFY 的 record 描述列举（课程/作业/考试/待办/日程/老师通知）漏了"实习/招聘信息"，而 match_analysis/study_plan 的描述里有"实习""JD"关键词 → 模型被带走
- 修法：record 明确覆盖"粘贴 JD 原文"，能力意图强调"用户明确要求"（双向收窄）

### 2. 提示词修复要靠多条真实样本验证

- 测试中一条样本过滤不代表稳定，还需要靠真实走查覆盖不同形态的输入看能不能正常使用

### 3. 正则 vs LLM 的边界（能写规则的别指望模型）

- delete/correct用 LLM 抽序号——因为要同时识别"类型（作业/待办/实习…）+ 序号"，需要语义理解
- pickInternship用正则抠序号——因为match_analysis意图已确定类型是实习，只剩数字
- 原则：机械固定的交给代码，需要理解的交给模型

### 4. 序号定位机制的第二次复用

- recordsWithSeq()（用来显示序号，返回快照）+ resolveIdBySeq(snapshot, type, seq)（得到序号→真实 id）
- 统一的编号体系：面板显示序号 = "删除实习第1条" = "分析实习第1条"（用户不用记两套） 

### 5. 两层判断的完备性（库空 vs 序号错）

- 第一层：先 repo.allInternships().isEmpty() → "还没有实习记录"（引导录入）
- 第二层：再 pickInternship → 空 → "没找到该编号的实习"（序号错）
- 为什么第二层一定是序号错：库非空时，无序号会走max(id)必定有值，不会返回空，返回空只可能是有序号，但是序号不存在

### 6. Optional 链：flatMap vs map

- findInternship 返回 Optional<InternshipItem>
- map(fn) → Optional<Optional<...>>（嵌套两层）；flatMap(fn) → 扁平化成 Optional<...>
- repo::findInternship等价于lambda表达式 id -> repo.findInternship(id)

### 7. find() vs matches()

- String.matches()用来整体匹配字符串，整体是否符合格式
- Pattern/Matcher.find()用来搜索字串，找有没有，在哪里
- group(1) 取第 1 个捕获组（group(0) 是整个匹配）——与 resolveDate 里的用法相同

## 文件与方法链路

按序号分析链路：
"分析实习第2条的匹配度" → handleStreaming → classify(match_analysis)
→ repo.allInternships().isEmpty()?（库空→提示录入）
→ pickInternship(input)：正则抠"第2条" → 2 → resolveIdBySeq(recordsWithSeq(), "internship", 2)
→ Optional<Long>（真实 id）→ flatMap(repo::findInternship) → Optional<InternshipItem>
→ 空则提示"没找到该编号"；否则 profile() 取档案
→ MATCH_ANALYSIS.replace({profile}).replace({jd}) → streamAnswer → 流式输出
