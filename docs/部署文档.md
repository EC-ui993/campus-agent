# 部署文档：一键起全栈

> 一条命令起 `nginx + app + mysql` 三件套。本文档记录**实际做过的步骤**与**真实踩过的坑**。

## 架构

```
浏览器 / 手机
     │  :8088
     ▼
┌──────────┐   http://app:8080    ┌──────────┐   mysql:3306   ┌──────────┐
│  nginx   │ ───────────────────► │   app    │ ─────────────► │  mysql   │
│ 唯一对外  │                      │ Spring   │                │  8.4     │
│ 开的口子  │                      │ Boot 3   │                │ 命名卷   │
└──────────┘                      └──────────┘                └──────────┘
     └───────────── Compose 内部网络（服务名即主机名）──────────────┘
                                          │
                     对外只出站：DeepSeek API（https）
```

| service | 镜像 | 对外端口 | 作用 |
|---|---|---|---|
| `nginx` | `nginx:alpine` | **8088** | 反向代理，唯一入口 |
| `app` | `campus-agent`（本地构建） | 无（仅内部 8080） | Spring Boot 应用 |
| `mysql` | `mysql:8.4` | 无（仅内部 3306） | 数据库 + 命名卷 `mysql-data` |

**`ports` 只在 nginx 上出现是刻意的**：`ports` 是"对宿主机开的口子"，不是"容器间的通道"。数据库完全藏在内部网络里。

**为什么对宿主机用 8088 而不是 80**：宿主机 80 容易被系统服务或其他工具占用，而且 Windows 上会出现"`up` 不报错、连接却被别的进程接走"的情况（见排障表最后一条）。容器内 nginx 仍然监听 80，只是换了个对外窗口。

## 快速开始

```bash
# 1. 准备 .env（同目录，已被 gitignore）
MYSQL_ROOT_PASSWORD=<自定义 root 密码>
MYSQL_PASSWORD=<campus 账号密码>
DEEPSEEK_API_KEY=<你的 key>

# 2. 起全栈
docker compose up -d --build

# 3. 打开
http://localhost:8088
```

首次 `up` 会自动：拉取 `mysql:8.4` / `nginx:alpine` → 用仓库根的 `Dockerfile` 构建 `campus-agent` → 建库 `agent` 与账号 `campus` → 等 mysql 健康 → 起 app → app 执行 `schema.sql` 建 13 张表 → 起 nginx。

## 环境变量

Compose 从同目录 `.env` 取值（用于 **yml 里的 `${...}` 插值**），再通过 `environment:` 传给容器。

| 变量 | 传给谁 | 说明 |
|---|---|---|
| `MYSQL_ROOT_PASSWORD` | mysql | root 密码；healthcheck 在容器内用它 |
| `MYSQL_PASSWORD` | mysql、app | `campus` 账号密码，两边必须一致 |
| `DEEPSEEK_API_KEY` | app | 模型 API key |
| `DB_HOST`（写在 yml 里） | app | 固定 `mysql`——**容器内不能用 `localhost`** |

> ⚠️ **`localhost` 在容器里指"这个容器自己"。** 所以 `application.yml` 里写的是
> `jdbc:mysql://${DB_HOST:localhost}:3306/agent?...`：宿主机直跑用默认 `localhost`，容器里由 Compose 注入 `DB_HOST=mysql`。
> **同一份配置适应两种运行环境。**

## 数据

**首次启动是空库**——Compose 的 mysql 是**独立实例 + 独立卷**，跟你本地那套 MySQL 的数据互不相通。

想让它带上既有数据，用导出的 dump：

```bash
# 把 dump 拷进容器，再在容器内执行（< 由容器里的 sh 处理，不需要 cmd /c）
docker cp data/dump.sql "$(docker compose ps -q mysql):/tmp/dump.sql"
docker compose exec -T mysql sh -c 'mysql -uroot -p$MYSQL_ROOT_PASSWORD --default-character-set=utf8mb4 agent < /tmp/dump.sql'
```

> **dump 的价值**：它让"重建环境"变成**可重复的动作**，而不是"再手动搬一次"。
> 本地那套 MySQL、Compose 这套 MySQL，都是靠它长出同一份数据的。

## 验证清单

| # | 命令 / 操作 | 通过标准 |
|---|---|---|
| 1 | `docker compose ps` | 三个服务 `running`，mysql 显示 **`(healthy)`** |
| 2 | `docker compose ps` 的 PORTS 列 | **只有 nginx** 有 `0.0.0.0:8088->80`；app/mysql 只有 `8080/tcp` / `3306/tcp` |
| 3 | `docker compose exec -T mysql mysql -ucampus -p<密码> agent -e "SHOW TABLES;"` | 列出 **13 张表** |
| 4 | 浏览器 http://localhost:8088 **发一条消息** | 回答**一个字一个字往外蹦**（流式） |
| 5 | 手机同 WiFi 打开 `http://<局域网IP>:8088` | 页面正常 |

> 第 4 条**不能用"页面能打开"代替**。`proxy_buffering` 只影响流式输出，页面和普通请求全都正常。

## 排障

| 现象 | 原因 | 解法 |
|---|---|---|
| 页面能开，但回答"等十几秒后整段一次性蹦出" | nginx 缓冲了 SSE | `docker/nginx.conf` 里必须有 `proxy_buffering off;`，且确认**已挂载**（`docker compose config` 可看） |
| 首次 `up` 后 app 崩溃，再 `up` 一次就好了 | `depends_on` 只保证启动顺序，不等"能用" | 已用 `healthcheck` + `condition: service_healthy` 解决 |
| app 报 `Communications link failure` / 连不上数据库 | 容器内用了 `localhost` | `DB_HOST=mysql`，且 `application.yml` 用 `${DB_HOST:localhost}` |
| app 报 `Access denied` | `MYSQL_PASSWORD` 与 mysql 侧不一致 | 两个变量同源（都取 `${MYSQL_PASSWORD}`） |
| **页面能用、数据也对，但改的代码没生效** | **镜像里是旧代码** | `docker compose up -d --build`。**最危险的一类失败：不报错，只是跑了旧版本** |
| `docker build` 报 `failed to read dockerfile` | 不在项目根目录 | `cd` 到仓库根再执行（`.` 是构建上下文） |
| `docker compose exec ... sh -c "..."` 里的 SQL 被拆散（报 `USE must be followed by a database name`） | **PowerShell 5.1 传参时会丢掉内嵌双引号**，SQL 被按空格拆开 | 别用 `sh -c` 套内嵌双引号；直接 `mysql ... -e "SQL"`（顶层双引号传参），或借 `cmd /c` |
| `docker build` 卡在 `mvn` 下载 | 构建容器访问 Maven 中央仓库不通 | 把 `settings.xml`（含国内镜像）`COPY` 进构建阶段，别依赖宿主机 `~/.m2` |
| 手机打不开，电脑正常 | Windows 防火墙挡住端口 / 手机与电脑不在同一网段 | 放行 8088 端口；确认同一 WiFi；校园网可能开了客户端隔离，用手机热点验证 |
| **`localhost:8088` 正常，但用局域网 IP 访问返回一个"不是 nginx 的 404"** | **宿主机该端口被别的进程（或网关）接走了**。判据：响应头里**没有 `Server: nginx`**，且 `Content-Length: 0` | 换一个宿主机端口（改 `ports` 左边）；查占位者：`Get-NetTCPConnection -LocalPort <端口> -State Listen`，再 `Get-Process -Id <PID>` |
| 想在宿主机直接连这台 MySQL | mysql 没有 `ports`（刻意） | 用 `docker compose exec` 进去；或临时加 `ports: "3307:3306"`（注意别跟本地 3306 冲突） |

## 常用命令

```bash
docker compose up -d --build     # 起（改了代码要带 --build）
docker compose ps                # 看状态（健康检查结果在这）
docker compose logs -f app       # 跟 app 日志
docker compose logs --tail=20 nginx   # 看 nginx 访问日志
docker compose restart app       # 只重启 app
docker compose exec app sh       # 进 app 容器
docker compose down              # 停并删容器，【保留】mysql-data 卷
docker compose down -v           # 连数据卷一起删（数据全没，谨慎）
```

## 已知限制

1. **`app` 没有 healthcheck**：`eclipse-temurin:17-jre` 镜像里没有 `curl`/`wget`，做不了 HTTP 探活。所以 nginx 可能先就绪，**开头几秒访问是 502**，刷新即可（nginx 不会因此崩溃）。要彻底解决得往镜像装 HTTP 客户端，代价是镜像变大。
2. **nginx 是 HTTP（8088），没有 TLS**。仅限本机 / 局域网使用；对外暴露必须上 HTTPS。
3. **没有版本化数据库迁移**：`schema.sql` 只管"从零建库"，对已存在的库不做任何事。`agent` 与 Compose 里的这个 MySQL 是两套独立环境，**改 schema 时要记得两边都对齐**（手动 `ALTER`）。等"记不住哪个库跑到哪一版"时，就该引入 Flyway。
